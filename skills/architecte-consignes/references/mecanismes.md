# Mécanismes vérifiés : comment Claude lit ses consignes

Référence factuelle du skill. Lire ce fichier avant d'expliquer un mécanisme à l'utilisateur ; ne rien affirmer qui n'y figure pas. Vérifié le 22/11/2026 sur la documentation officielle, sections 1 à 15, et complété le 24/11/2026 au §6 (sources datées en fin de section) ; ce qu'elle ne décrit pas est marqué « non documenté ». La documentation évolue vite : revérifier avant chaque nouvelle version. Version de Claude Code : `claude --version` dans un terminal ; dans l'onglet Code de l'application de bureau, `/status`, ligne « Claude Code ». Ces deux copies peuvent avoir des versions différentes.

## 1. Où Claude Code cherche ses consignes

| Portée | Emplacement | Chargement |
|---|---|---|
| Organisation (géré par l'informatique) | macOS `/Library/Application Support/ClaudeCode/CLAUDE.md` ; Linux et WSL `/etc/claude-code/CLAUDE.md` ; Windows `C:\Program Files\ClaudeCode\CLAUDE.md` ; ou clé `claudeMd` des réglages gérés, sans fichier | Au lancement, en premier |
| Utilisateur, tous les projets | `~/.claude/CLAUDE.md` (sous Windows : `C:\Users\<nom>\.claude\CLAUDE.md`) | Au lancement |
| Projet, partagé | `./CLAUDE.md` ou `./.claude/CLAUDE.md` (les deux dans le même dossier : non documenté, à vérifier dans l'application ; en attendant, n'en garder qu'un) | Au lancement |
| Projet, personnel | `./CLAUDE.local.md`, à exclure du partage (par exemple dans `.gitignore`) | Au lancement, juste après le CLAUDE.md du même dossier |
| Dossiers parents | `CLAUDE.md` et `CLAUDE.local.md` de chaque dossier au-dessus du dossier de lancement | Au lancement |
| Sous-dossiers | `CLAUDE.md` et `CLAUDE.local.md` d'un sous-dossier du dossier de lancement ; règles du `.claude/rules/` d'un sous-dossier | À la demande : dès que Claude lit, écrit ou modifie un fichier de ce sous-dossier, ou en lit un par une commande comme `cat` ou `head` (une commande shell quelconque ne suffit pas) |
| Règles | `.claude/rules/**/*.md`, et `~/.claude/rules/` pour tous les projets | Sans `paths` : au lancement. Avec `paths` : quand Claude touche un fichier visé |

Hors `AGENTS.md` (§9) et les règles de `.claude/rules/`, seuls ces noms sont chargés. Un fichier `MODELE-CLAUDE.md`, `CLAUDE.ancien.md` ou `consignes/contexte.md` n'est jamais chargé de lui-même. Dans `.claude/rules/` et `~/.claude/rules/`, en revanche, tout fichier `.md` est chargé, quel que soit son nom, sous-dossiers compris : la copie de sauvegarde d'une règle se range hors de ce dossier. À l'inverse, un vrai `CLAUDE.md` laissé dans un dossier d'archives ou de modèles redevient une consigne active dès que Claude lit un fichier voisin. Pour l'éviter, le renommer, ou l'exclure avec le réglage `claudeMdExcludes`. Ce réglage prend une liste de motifs comparés aux chemins absolus des fichiers de consignes, par exemple `"claudeMdExcludes": ["**/archives/**"]`. Il se place dans les réglages utilisateur, projet, local ou gérés, et les listes s'additionnent ; le CLAUDE.md géré par l'organisation ne peut pas être exclu. Vérifier ensuite l'effet. Pour un fichier chargé au lancement (dossier parent) : `/context all`. Pour un CLAUDE.md de sous-dossier, chargé à la demande, `/context all` ne le montre jamais, exclu ou non : faire lire à Claude un fichier voisin et vérifier qu'aucune ligne « Loaded » suivie de son chemin n'apparaît dans le terminal, ou tracer les chargements avec un hook `InstructionsLoaded` (§10).

Dossiers ajoutés avec `--add-dir` : leurs CLAUDE.md ne sont pas chargés, sauf avec la variable `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1`.

Sous-agents : ils reçoivent les mêmes fichiers de consignes que la session, sauf les sous-agents intégrés Explore, Plan et web-fetch, et ceux réglés avec `omitClaudeMd: true`. Une consigne critique pour un sous-agent se répète dans la demande qui lui est faite.

Sources (22/11/2026) : https://code.claude.com/docs/en/memory ; https://code.claude.com/docs/en/sub-agents

## 2. Aucune priorité : tout s'additionne

Tous les fichiers trouvés sont mis bout à bout dans le contexte ; aucun n'en écrase un autre. L'ordre va du plus large au plus précis : le fichier le plus proche du dossier de lancement est lu en dernier. Si deux consignes se contredisent, Claude peut suivre l'une ou l'autre. Il ne faut donc pas compter sur un fichier local pour « annuler » une règle du parent : formuler la règle une seule fois, avec sa portée et ses exceptions. Il en va de même entre `~/.claude/rules/` et les règles du projet. La documentation dit qu'une règle sans `paths` se charge « avec la même priorité » que `.claude/CLAUDE.md` : même moment de chargement, pas de préséance.

Sources (22/11/2026) : https://code.claude.com/docs/en/memory

## 3. Les imports `@` organisent, ils n'allègent pas

- Syntaxe : `@chemin/fichier.md`, sur une ligne seule ou au milieu d'une phrase (« Voir @README »). Tout `@chemin` écrit hors accents graves et hors bloc de code est un import, sauf un chemin dont les guillemets entourent le chemin lui-même (pas la phrase qui le contient), qui n'est pas importé du tout. Le chemin relatif part du fichier qui contient l'import, pas du dossier de travail. Les chemins absolus sont admis ; l'exemple officiel utilise aussi `~`.
- Le fichier importé se charge en même temps que le fichier qui l'importe. Importer depuis le maître, c'est donc charger à chaque session : **aucune économie de contexte**.
- Imports en cascade : quatre sauts au plus.
- Les imports écrits dans un `code span` ou un bloc de code sont ignorés : pour citer un chemin sans l'importer, l'écrire entre accents graves.
- Un espace dans le chemin d'un import se protège par une barre oblique inverse (`@Mes\ docs/x.md`). Sans elle, le chemin s'arrête au premier espace ; entre guillemets, avec ou sans barre oblique inverse, il n'est pas importé. Plus simple : pas d'espace dans les noms des fichiers et dossiers de consignes.
- Dans un fichier de projet, un import qui sort du dossier de travail demande une approbation la première fois. En cas de refus, ces imports restent désactivés sans nouvelle demande. Les imports de `~/.claude/CLAUDE.md` ne demandent pas d'approbation, sauf dans les sessions Cowork sur le bureau, où ceux qui sortent du dossier de la session sont sautés (voir §12).
- Une phrase comme « lis tel fichier » n'est pas un import : Claude ne voit le fichier que s'il décide de l'ouvrir.

Sources (22/11/2026) : https://code.claude.com/docs/en/memory

## 4. Les quatre manières de taguer un fichier satellite

| Écriture | Quand le contenu est chargé | Coût de contexte | Usage |
|---|---|---|---|
| `@consignes/contexte.md` dans le maître | À chaque session, avec le maître | Permanent | Ce dont chaque session a besoin |
| « Avant de [tâche], lire `consignes/x.md` » | Si Claude suit la consigne | Seulement à l'usage | Référence ponctuelle ; lecture non garantie |
| `.claude/rules/x.md` avec `paths:` | Quand Claude lit, écrit ou modifie un fichier visé | Seulement à l'usage | Règles propres à un dossier ou à un type de fichier |
| Skill `.claude/skills/x/SKILL.md` | Nom visible en permanence, description si la place le permet (§11) ; contenu à l'appel (`/x`) ou quand Claude juge le skill utile | Faible | Procédure récurrente |

Syntaxe des `paths` : liste YAML, ou chaîne séparée par des virgules, de motifs relatifs au dossier qui contient `.claude` ; pour une règle de `~/.claude/rules/`, relatifs au dossier de lancement. Exemples : `**/*.ts`, `src/**/*`, `*.md` (tous niveaux), `/*.md` (base seulement), accolades pour plusieurs extensions (`*.{docx,xlsx}`). Un `[` littéral s'échappe (`'photos \[2024/**'`). Seul le champ `paths` est lu dans le frontmatter d'une règle. Mettre entre guillemets un motif qui commence par `*` ou `{`, par exemple `- "**/*.md"` : si le YAML ne se lit pas, le frontmatter est ignoré et la règle se charge à chaque session, comme sans `paths`, sans signal (erreur visible avec `claude --debug`).

Sources (22/11/2026) : https://code.claude.com/docs/en/memory

## 5. Taille et rédaction

- Cible officielle : moins de 200 lignes par CLAUDE.md. Au-delà, le fichier coûte plus de contexte et ses consignes sont moins bien suivies.
- Fichiers chargés à la demande (CLAUDE.md et CLAUDE.local.md de sous-dossier et leurs imports, règles d'un `.claude/rules/` de sous-dossier, règles par chemin) : au-delà d'une limite de caractères, seul le début est lu (version 2.1.309 ou ultérieure). La limite est de 40 000 caractères avec une fenêtre de 200 000 tokens. Avec une fenêtre d'un million, elle passe à 200 000 caractères sur Claude Opus 4.6 et Sonnet 4.6, et à 150 000 sur les modèles plus récents. Un CLAUDE.md chargé au lancement est lu en entier jusqu'à 4 Mio ; au-delà, il est ignoré en entier.
- Un avertissement, au démarrage et dans `/status`, signale un fichier plus long que recommandé, ou des fichiers trop lourds au total (chaque CLAUDE.md, règle et import compte).
- Consignes concrètes et vérifiables : « indenter de deux espaces » plutôt que « formater proprement ».
- Titres et listes plutôt que paragraphes denses ; relecture régulière pour retirer l'obsolète et le contradictoire.
- Emphase déconseillée : « IMPORTANT » et les majuscules aidaient d'anciens modèles ; aujourd'hui, cette emphase fait surtout sur-appliquer la règle. Une règle qui ne doit jamais céder devient un hook ou une règle deny.
- Les commentaires HTML de bloc (`<!-- … -->`) d'un CLAUDE.md sont retirés avant l'envoi à Claude, sauf dans un bloc de code : on peut y laisser des notes de maintenance sans coût. Ils restent visibles si Claude ouvre le fichier pour le lire. La documentation ne le garantit que pour les CLAUDE.md : dans un satellite, une règle ou un skill, un commentaire peut rester visible.

Sources (22/11/2026) : https://code.claude.com/docs/en/memory ; https://code.claude.com/docs/en/best-practices

## 6. Une consigne n'est pas une garantie

- Un CLAUDE.md est du contexte : Claude le lit et essaie de le suivre, sans garantie. Les réglages (permissions) et les hooks, eux, sont appliqués par l'outil, quoi que décide Claude.
- Permissions : listes `allow`, `ask` et `deny` dans `~/.claude/settings.json` (utilisateur), `.claude/settings.json` (projet, partagé) et `.claude/settings.local.json` (projet, personnel). Les listes de tous les fichiers s'additionnent ; l'ordre d'évaluation est deny, puis ask, puis allow. Un deny l'emporte sur tout allow, quel que soit le fichier, et sur la réponse d'un hook. Exception documentée : un mod (plugin qui exécute du code dans Claude Code) peut approuver certains appels refusés par un deny ou bloqués par un hook, quand la session n'a ni réglages gérés, ni `managed-mcp.json`, ni connexion Team ou Enterprise (cas d'un compte Pro ou Max, ou d'une clé API). N'installer que des mods de confiance.
- Mode de permission : en terminal et dans l'extension VS Code (version 2.1.283 ou ultérieure), une session démarre par défaut en mode auto (sauf option `--permission-mode`, ou `defaultMode` ou `disableAutoMode` dans les réglages) ; `claude -p` démarre en mode manuel. Dans l'onglet Code de l'application de bureau, vérifier le sélecteur sous la zone de saisie avant le premier message (choix retenu par dossier). En mode auto, un classifieur examine les actions à la place de l'utilisateur : les modifications de fichiers dans le dossier de travail passent sans demande, et les allow larges (`Bash(*)`, interpréteur avec joker) sont écartés. Les deny bloquent dans tous les modes. Une règle ask fait demander dans tous les modes, sauf en mode `dontAsk`, où l'appel est refusé (exception des mods ci-dessus). En mode auto, après 3 blocages de suite ou 20 au total, Claude Code redemande. Le classifieur du mode auto laisse passer par défaut un push vers toute branche du dépôt de travail, branche par défaut comprise (une branche de déploiement comme `production` ou `gh-pages` est jugée à part) ; un force push reste bloqué par défaut, et un deny arrête toujours un push écrit sous la forme qu'il vise. `defaultMode` à `auto` ou `bypassPermissions` est sans effet dans les réglages projet et local. Cowork a ses propres modes (Manual, Auto, Skip).
- Le `.claude/settings.json` partagé est lu depuis le dossier de travail de la session. Une session ouverte dans un sous-dossier ne reçoit donc pas les deny du `.claude/settings.json` du parent : lancer Claude à la racine, ou répéter les deny dans le sous-dossier en réécrivant les motifs `./`, qui partent du dossier de lancement (`Read(./clients/rh/**)` devient `Read(./rh/**)` dans `clients/`), ou en chemin absolu (`//c/…`). En terminal, `/status` (ligne « Setting sources ») ou `/permissions` montrent les réglages chargés, pas le chemin qu'une règle vise. Dans toutes les interfaces, tester donc chaque deny réécrit sur un fichier factice, dans une session ouverte au dossier voulu : la lecture demandée à Claude doit être refusée. Dans l'onglet Code, `/permissions` est indisponible.
- Syntaxe : `Outil(spécificateur)`, par exemple `Read(./.env)`, `Bash(npm run test *)`, `WebFetch(domain:example.com)`, `Skill(deploy *)`. Le nom d'outil seul, sans parenthèses (`WebFetch`, `WebSearch`, `Bash`), vise tous ses usages. Une règle Bash sans `*` vise une seule commande exacte. Le `*` remplace n'importe quel texte, à n'importe quelle place ; en fin de règle, précédé d'une espace, il couvre aussi la commande nue (`Bash(git log *)` couvre `git log`), mais seulement si ce `*` final est le seul joker de la règle : `Bash(* --help *)` ne couvre pas `npm --help`, ni `Bash(git push * main *)` la commande `git push origin main`. La forme `Bash(cmd:*)` équivaut à `Bash(cmd *)` : `Bash(ls:*)` vise les mêmes commandes que `Bash(ls *)`. Ce `:*` n'est reconnu qu'en fin de règle ; dans `Bash(git:* push)`, les deux-points sont un caractère ordinaire et la règle ne vise aucune commande git. Dépréciation de la forme `:*` : non documentée ; la demande d'autorisation, elle, écrit la forme avec espace. L'outil PowerShell de Claude Code, sous Windows, suit la même forme : `PowerShell(commande *)`. Ses alias courants sont ramenés au nom de la cmdlet avant la comparaison : `PowerShell(Get-ChildItem *)` vise aussi `gci`, `ls` et `dir`. La liste exacte des alias reconnus n'est pas documentée : pour `Remove-Item`, `del`, `ri` et `rm` sont probables (non documenté, à vérifier dans l'application). La comparaison PowerShell ignore la casse, et chaque sous-commande (`|`, `;`) est vérifiée.
- Connecteur (MCP) : viser l'outil par son nom canonique, `mcp__<serveur>__<outil>`, sans parenthèses. Ce nom peut différer du libellé de la demande d'autorisation, et les règles ne reconnaissent pas les libellés. En terminal ou dans VS Code, un connecteur claude.ai s'écrit `mcp__claude_ai_<Serveur>__<outil>` (points et espaces deviennent `_`). Dans l'onglet Code de l'application de bureau, le serveur peut porter un identifiant au lieu du nom (constaté le 22/11/2026, non documenté) : demander à Claude le nom exact de l'outil dans sa liste. Aucun avertissement ne signale un nom `mcp__` erroné. Un deny sur un nom d'outil seul retire l'outil de la liste de Claude : ouvrir une nouvelle session et vérifier que Claude ne le voit plus. Un deny accepte aussi un motif sur le nom (`mcp__*` vise tous les outils MCP), par exemple `mcp__*__send_message` (à vérifier dans l'application). Tous les outils d'un serveur : `mcp__<serveur>__*`, ou `mcp__<serveur>` seul. En allow, un joker n'est admis qu'après ce préfixe littéral : `mcp__*` en allow n'autorise rien. Une règle `mcp__` suivie de parenthèses est ignorée au chargement des réglages ; elle est signalée au démarrage d'une session interactive et par `claude doctor`.
- Fichier `.mcp.json`, à la racine du projet : il déclare les serveurs MCP de portée projet, sous la clé `mcpServers`. La documentation le destine au dépôt partagé, pour que toute l'équipe ait les mêmes serveurs. Déduction : une valeur écrite en clair dans ce fichier est partagée avec lui. Les serveurs de portée locale (ce projet, pour soi seul) et utilisateur (tous les projets) sont rangés, eux, dans `~/.claude.json`, fichier que Claude Code tient lui-même (compte, état des projets, serveurs MCP). Les outils d'un serveur se nomment `mcp__<serveur>__<outil>`, avec le nom donné au serveur (points et espaces devenus `_`). Un serveur `stdio` est un programme lancé sur l'ordinateur par `command` et `args`, par exemple `npx -y paquet`. Déduction, la documentation ne le dit pas : sans version fixée (`paquet@1.2.3`), le code lancé peut changer d'une session à l'autre. La documentation demande de vérifier qu'on fait confiance à chaque serveur avant de le connecter.
- Approbation des serveurs de `.mcp.json` : en session interactive, Claude Code demande l'accord avant d'utiliser chacun ; `claude mcp reset-project-choices` efface les réponses. Ces réponses s'écrivent dans `.claude/settings.local.json`, sous trois réglages admis dans tout fichier de réglages. `enableAllProjectMcpServers: true` approuve tous les serveurs du fichier. `enabledMcpjsonServers` approuve une liste de noms. `disabledMcpjsonServers` rejette une liste de noms, dans tous les modes de permission, depuis n'importe quel fichier, `.claude/settings.json` partagé compris ; ce rejet l'emporte sur les deux approbations. Dans un dossier non approuvé, une approbation écrite dans le `.claude/settings.json` partagé est ignorée : un dépôt n'approuve pas ses propres serveurs. Un serveur pas encore approuvé apparaît « Pending approval » dans `claude mcp list` et `claude mcp get`. Déduction : ses outils manquent alors à la liste de Claude, deny ou non ; leur absence ne prouve donc pas un deny. Sans demande possible, les serveurs du projet sont connectés sans accord : `claude -p`, Agent SDK, sessions cloud hors fils d'un projet, mode `bypassPermissions` avec `skipDangerousModePermissionPrompt`. Dans une tâche locale programmée de l'application de bureau : non documenté, à vérifier dans l'application. Pour écarter un serveur dans tous les cas : `disabledMcpjsonServers`.
- Variables dans `.mcp.json` : une valeur de `command`, `args`, `env`, `url` ou `headers` peut citer une variable d'environnement. `${VAR}` donne sa valeur ; `${VAR:-défaut}` donne sa valeur, ou `défaut` si elle n'est pas définie. La documentation présente ce moyen pour partager le fichier sans y écrire les clés d'API. Une variable non définie et sans défaut n'empêche pas le chargement : `claude mcp list` la signale, et le texte `${VAR}` est transmis tel quel. Une variable vide compte comme définie. Dans `url` et `headers` d'un serveur distant, certains noms de secrets valent toujours vide, sans avertissement : ceux de Claude Code (`ANTHROPIC_API_KEY`), ceux du fournisseur cloud, et d'autres comme `NPM_TOKEN`. Choisir donc un nom propre au serveur. `/mcp`, `claude mcp list` et `claude mcp get` affichent la référence `${VAR}`, pas sa valeur. Déduction : la variable se définit dans l'environnement qui lance Claude Code (variables d'environnement de l'utilisateur, ou terminal). Prise en compte du bloc `env` des réglages : non documentée, à vérifier dans l'application.
- Cowork : Claude y lance les commandes par `mcp__workspace__bash` et les récupérations web par `mcp__workspace__web_fetch`. Un deny qui vise l'outil `Bash` ou `WebFetch` entier vaut aussi pour ces outils. La documentation donne l'exemple d'un deny des réglages gérés par l'organisation ; écrit dans les réglages utilisateur ou projet (`~/.claude/settings.json`, `.claude/settings.json`), son effet dans Cowork n'est pas documenté : à vérifier dans l'application. Un allow `Bash` ne s'y applique jamais.
- Motifs de chemin des règles Read et Edit : syntaxe de type gitignore. Le `*` remplace du texte à l'intérieur d'un seul élément du chemin : il s'arrête à `/`. Le `**` traverse les dossiers : `Read(./secrets/**)` vise le contenu de `secrets`, sous-dossiers compris. Déduction : `dossier/*` vise les éléments placés directement dans `dossier`. Son effet sur les fichiers des sous-dossiers n'est pas documenté : à vérifier dans l'application. Pour viser tout le dossier, écrire `dossier/**`. Un nom de fichier seul vaut à toute profondeur sous le dossier de lancement : `Read(.env)` équivaut à `Read(**/.env)`. Un motif relatif d'un seul dossier, comme `secrets/**`, vise en deny et en ask tout dossier de ce nom, à toute profondeur ; en allow, le seul `secrets` du dossier de lancement. Cette différence pour la forme `./secrets/**` : non documentée, à vérifier dans l'application. `//chemin` part de la racine du disque, `~/chemin` du dossier personnel, `./chemin` ou `chemin` du dossier de lancement. `/chemin` part du dossier de lancement dans `.claude/settings.json` et `.claude/settings.local.json`, de `~/.claude` dans `~/.claude/settings.json`, et du dossier du fichier pour un fichier passé avec `--settings`. Une règle utilisateur qui doit valoir dans tous les projets s'écrit donc en `//` ou en `~/`. Sous Windows, un lecteur s'écrit `//c/…`. Casse des motifs Read et Edit : non documentée (seules les règles PowerShell et `WebFetch(domain:)` l'ignorent), à vérifier dans l'application.
- Une règle `Edit(...)` couvre tous les outils intégrés qui modifient un fichier, dont Write : création et écrasement compris. Une règle `Write(...)` n'est pas appliquée. Un deny `Read(...)` bloque aussi Edit et Write sur le même chemin, création comprise (Write : version 2.1.228 ou ultérieure).
- Portée d'un deny de lecture : il s'applique aux outils Read, Grep et Glob (au mieux), aux commandes de lecture Bash reconnues (`cat`, `head`, `tail`, `sed`, `tee`) et aux redirections. Il ne couvre ni un `grep -r` lancé dans le dossier, ni un script qui ouvre le fichier lui-même. Son effet sur une commande de l'outil PowerShell (`Get-Content`, `type`, `Set-Content`) n'est pas documenté : à vérifier dans l'application. Un secret doit donc rester hors de l'espace de travail ; le deny n'est qu'une protection de plus.
- Une règle Bash porte sur le texte de la commande, pas sur le programme : `Bash(rm *)` ne bloque pas `bash -c 'rm …'`, `/bin/rm` ou `sh -c`, et `Bash(git push *)` ne bloque ni `git -C . push` ni `git -c … push`. D'après ces règles, `Bash(git push * main)` arrête `git push origin main`, mais pas `git push origin HEAD:main` : une mention « bloqué » ne vaut que pour les formes couvertes. Un allow à préfixe sur `npx` ou `docker exec` autorise toute commande lancée derrière. La documentation ne cite pas `python -c *` ni `node -e *`, mais il découle de son principe qu'une autorisation large sur un interpréteur laisse passer n'importe quel code. De même (déduction, la documentation ne cite pas ce cas), une commande nommée qui exécute du code du dépôt (script npm ou make, lanceur de tests) laisse passer ce code. Un script du dépôt modifié puis lancé échappe donc aux deny de lecture (puce précédente) et aux règles Bash ou PowerShell, deny comme ask, qui ne voient que la commande qui le lance. Le risque existe dès que ce code se modifie sans demande : en mode Accept edits ou auto, Claude modifie sans demande les fichiers du dossier de travail. Les chemins protégés font exception (par exemple `.git`, `.claude`, `.husky`, `.npmrc` ; liste complète dans la documentation) : le mode Accept edits demande, le mode auto s'en remet au classifieur.
- Commandes réseau : un deny `WebFetch` (nom seul) retire l'outil WebFetch, mais n'empêche pas l'accès au réseau. Si Bash reste permis, Claude peut encore joindre n'importe quelle adresse par `curl`, `wget` ou un autre programme ; la commande relève alors des règles Bash, qui portent sur son texte (puce précédente), et du mode de permission. Il en va de même, par déduction (la documentation ne cite que `WebFetch` et Bash), d'un deny `WebSearch` ou d'un outil de connecteur, et d'une commande de l'outil PowerShell (`Invoke-WebRequest`).
- Outil `Artifact` : il publie sur claude.ai une page construite à partir de ce que la session peut lire (fichiers, connecteurs), privée jusqu'au partage. Il existe en terminal et dans l'application de bureau (version 1.13576.0 ou ultérieure), si la session est connectée par `/login` à un compte claude.ai Pro, Max, Ultra, Team ou Enterprise ; pas avec une clé API, ni chez un fournisseur cloud (Bedrock, Google Cloud, Foundry), ni par défaut avec `claude -p`. Claude peut publier de lui-même. Une publication faite en réponse à un message tapé, y compris, par déduction, une publication que Claude décide seul pendant ce tour, passe sans demande d'autorisation ni examen du classifieur, sauf cas listés par la documentation (mode plan, page partagée publiquement, etc.). `Artifact` dans `deny` désactive l'outil, comme `"enableArtifact": false` ou la ligne « Artifacts » de `/config` ; un deny `WebFetch` sans `domain:` ne le désactive pas.
- Répondre « Oui, ne plus demander » à une commande Bash ou à un domaine web écrit une règle `allow` dans `.claude/settings.local.json`, à la racine du dépôt git (à côté de `.claude/settings.json` sous Windows ou hors git). Pour une modification de fichier, l'accord vaut jusqu'à la fin de la session, sans être enregistré. Cette liste grossit au fil des clics : la relire à chaque revue des consignes. Les `allow` d'un `.claude/settings.json` partagé attendent que le dossier soit approuvé ; les `deny` et `ask` s'appliquent tout de suite.
- Hook : commande lancée à un moment précis du cycle (par exemple avant chaque outil). Un hook PreToolUse qui sort avec le code 2 bloque l'appel, comme un deny (même exception pour les mods). Les règles deny et ask restent évaluées quel que soit le retour du hook : un hook ne lève donc pas un deny.

## 7. Après une compaction du contexte

Le CLAUDE.md à la racine du projet, les règles sans `paths` et la mémoire automatique sont relus sur le disque et réinjectés. Les CLAUDE.md de sous-dossiers et les règles par chemin reviennent seulement quand Claude retouche un fichier concerné. Une consigne donnée uniquement dans la conversation peut disparaître : si elle doit durer, l'écrire dans le maître. Les skills déjà appelés sont réinjectés dans la limite de 5 000 tokens par skill et 25 000 au total, les plus anciens tombant en premier. Seul leur début peut donc survivre, d'où l'intérêt de placer leurs règles essentielles en tête.

## 8. Mémoire automatique

- Emplacement : `~/.claude/projects/<projet>/memory/`, avec un index `MEMORY.md` et un fichier par souvenir. Au démarrage, Claude charge les 200 premières lignes ou les 25 premiers Ko de l'index, au premier des deux seuils atteint ; les autres fichiers sont lus à la demande.
- Portée : le dépôt git, tous ses sous-dossiers et worktrees compris ; hors dépôt git, la racine du projet. Un sous-dossier ouvert seul hors git a donc sa propre mémoire. La mémoire reste sur la machine et ne se charge pas dans les sous-agents.
- Activée par défaut ; réglable avec `/memory` ou le réglage `autoMemoryEnabled`.
- Rôle : retenir ce que Claude apprend. Claude y range aussi des notes de type `project` (travail en cours, échéances, décisions). Choix du kit : n'y mettre ni règle (portée partielle) ni état de référence.
- Dire « retiens que… » écrit en mémoire automatique. Pour une règle, dire « ajoute ceci au CLAUDE.md », ou passer par `/memory`.

Sources (22/11/2026) : https://code.claude.com/docs/en/memory

## 9. Plusieurs agents : AGENTS.md

- Par défaut, Claude Code lit `AGENTS.md` (depuis la version 2.1.277) seulement s'il ne trouve ni `CLAUDE.md`, ni `.claude/CLAUDE.md`, ni `CLAUDE.local.md` dans le dossier de travail ou au-dessus. Il lit alors aussi `.claude/AGENTS.md`, mais jamais `AGENTS.local.md`, `AGENTS.override.md` ni le contenu de `.agents/`. Ne comptent pas pour ce choix, et se chargent avec `AGENTS.md` : `~/.claude/CLAUDE.md`, même placé au-dessus du dossier de travail (espace rangé sous le dossier personnel), le CLAUDE.md géré par l'organisation et les règles de `.claude/rules/`.
- Ce comportement se règle par « Project instructions » : `/config` dans un terminal, ou `pluginConfigs` d'un fichier de réglages, clé `cc-plugin-agents-md@builtin` (`agents-md@builtin` avant la version 2.1.285), option `instructionFiles`. Cette entrée est lue dans `~/.claude/settings.json`, dans un fichier passé avec `--settings` ou dans les réglages gérés par l'organisation, et ignorée dans les réglages projet et local. Valeurs : `claude-md-or-agents-md` (défaut), `claude-md-and-agents-md`, `claude-md`, `managed-only` (au lancement, seulement le CLAUDE.md géré et la mémoire automatique).
- Un `CLAUDE.local.md` compte comme un CLAUDE.md : en créer un dans un projet qui n'a qu'un `AGENTS.md` fait cesser la lecture d'`AGENTS.md`, sans avertissement. Pour garder les deux, régler « Project instructions » sur `claude-md-and-agents-md`, ou créer un CLAUDE.md qui importe `@AGENTS.md`. Les préférences valables pour tous les projets vont dans `~/.claude/CLAUDE.md`.
- Un `AGENTS.md` de sous-dossier n'est lu à la demande, quand Claude ouvre un fichier de ce sous-dossier avec l'outil Read, que si aucun `CLAUDE.md`, `.claude/CLAUDE.md` ni `CLAUDE.local.md` n'existe dans le dossier de travail, au-dessus, ni dans ce sous-dossier. Avec un CLAUDE.md racine, il n'est donc pas lu par défaut : mettre à côté un CLAUDE.md qui commence par `@AGENTS.md`, ou régler « Project instructions » sur `claude-md-and-agents-md` (chaque dossier lit alors ses CLAUDE.md, puis son AGENTS.md).
- Montage documenté pour garder `AGENTS.md` comme source commune quand Claude ne le lit pas seul (projet qui a aussi un CLAUDE.md, réglage `claude-md`, session sans lecture d'AGENTS.md) : un `CLAUDE.md` à côté qui contient la ligne `@AGENTS.md`, suivie des seules consignes propres à Claude. L'import ne fait jamais lire AGENTS.md deux fois. Le lien symbolique est déconseillé sous Windows.
- Lecture directe d'`AGENTS.md` absente dans certains cas : plugin intégré qui lit `AGENTS.md` désactivé par `/plugin` ; première session après une mise à jour depuis la version 2.1.276 ou antérieure ; avant la version 2.1.281, certaines sessions (Bedrock, télémétrie coupée). Dans les deux premiers cas, comme avant la version 2.1.277, « Project instructions » n'apparaît pas dans `/config`. Un hook `InstructionsLoaded` ne se déclenche pas pour un AGENTS.md lu directement.
- Les autres agents (Codex, Cursor, etc.) ont leurs propres règles de découverte : se reporter à leur documentation.

Sources (22/11/2026) : https://code.claude.com/docs/en/memory

## 10. Commandes utiles

| Commande | Effet |
|---|---|
| `/init` | Analyse le dossier et propose un CLAUDE.md de départ ; un fichier existant n'est pas écrasé, des améliorations sont proposées. Avec `CLAUDE_CODE_NEW_INIT=1`, version interactive qui couvre aussi les skills et les hooks, et lit AGENTS.md. S'il trouve une configuration Codex ou Gemini CLI, il propose `/import`, qui recopie une fois AGENTS.md dans le CLAUDE.md : refuser si AGENTS.md doit rester la source commune (§9) |
| `/memory` | Ouvre ou crée les CLAUDE.md ; active ou désactive la mémoire automatique (dans l'onglet Code : non documenté) |
| `/context all` | Liste, sous « Memory files », les fichiers de consignes chargés au lancement et leur coût (en plein écran, `/context` seul replie cette liste). Un CLAUDE.md de sous-dossier, chargé à la demande, n'y figure pas ; pour une règle par chemin, non documenté, à vérifier dans l'application. Dans l'onglet Code, seul `/context` est documenté (répartition par catégorie) |
| `/status` | Terminal : version et ligne « Setting sources » (fichiers de réglages chargés). Onglet Code : ligne « Claude Code » (version) ; ligne « Setting sources » non documentée |
| `/permissions` | Terminal : règles allow, ask et deny, avec leur fichier. Onglet Code : répond « isn't available in this environment » ; modifier les fichiers de réglages |
| `/config` | Terminal : réglages, dont « Project instructions » (§9). Onglet Code : ouvre Settings > Code |
| `/doctor` | Propose des coupes pour un CLAUDE.md trop long ; `/doctor prompt-audit` (version 2.1.283 ou ultérieure) signale les consignes datées, les fichiers inexistants et les contradictions |

Suivre les chargements à la demande : dans le terminal, une ligne « Loaded » suivie du chemin s'affiche quand un CLAUDE.md de sous-dossier se charge. Un hook `InstructionsLoaded` journalise chaque chargement avec sa raison (`session_start`, `nested_traversal`, `path_glob_match`, `include`, `compact`).

Le raccourci `#` en début de message, cité par d'anciens guides, a été retiré en version 2.0.70 : dire « ajoute ceci au CLAUDE.md ».

## 11. Skills

- Emplacements : personnel `~/.claude/skills/<nom>/SKILL.md` ; projet `.claude/skills/<nom>/SKILL.md` ; plugin ; skills activés sur le compte claude.ai. Si deux skills portent le même nom, l'ordre de priorité est : entreprise, puis personnel, puis projet.
- Skills du compte claude.ai : chargés aussi par l'onglet Code de l'application de bureau, et par le terminal connecté avec ce compte par `/login` (version 2.1.273 ou ultérieure ; pas avec une clé API, ni en `--bare`). Le terminal les copie dans `~/.claude/skills/synced/`, écrasé à chaque synchronisation : ne rien y modifier. Si un skill local porte le même nom, `/nom` lance le skill local et `/anthropic-skills:nom` la copie du compte ; `/skills` les liste sous « claude.ai sync ». Le réglage `syncClaudeAiSkills: false` arrête la synchronisation. La page platform.claude.com dit encore que les skills ne se synchronisent pas entre surfaces.
- Chargement progressif : le nom et, si la place le permet, la description sont visibles en permanence ; le SKILL.md entier est lu à l'appel ; les fichiers annexes ne sont lus que si besoin. Les anciennes commandes `.claude/commands/` fonctionnent toujours et sont fusionnées dans les skills.
- Appel : `/nom` en début de message (le menu `/` et `/skills` listent les skills), ou décision de Claude d'après la description. Le champ `disable-model-invocation: true`, propre à Claude Code, réserve le skill à l'appel explicite : à utiliser pour une procédure qui envoie, publie ou supprime.
- Portabilité vers claude.ai : la spécification ouverte Agent Skills liste six champs, `name`, `description`, `license`, `compatibility`, `metadata` et `allowed-tools`. `name` compte 1 à 64 caractères (minuscules, chiffres, tirets, sans tiret au début, à la fin ni doublé) et reprend le nom du dossier. Pour un import sur claude.ai ou par l'API, `name` ne contient pas non plus les mots réservés `anthropic` et `claude`, même entre tirets ; Claude Code ne l'exige pas, mais un skill à partager s'y tient (vérifié le 22/11/2026 ; refus à l'import non constaté dans l'application). `description` compte 1 024 caractères au plus ; Claude Code, lui, tronque la description à 1 536 caractères dans sa liste. Selon la page Skills, claude.ai et l'API n'acceptent que ces six champs ; un autre champ, dont `disable-model-invocation`, fait échouer l'import (erreur « Unexpected key(s) ») au lieu d'être ignoré. Un skill à partager s'en tient donc à `name` et `description`.
- Le frontmatter n'est lu que si la ligne `---` d'ouverture est la toute première ligne du fichier.
- SKILL.md de moins de 500 lignes ; fichiers annexes cités depuis SKILL.md, sans cascade de renvois.

## 12. Cowork et claude.ai

- claude.ai : un skill s'importe en dossier zippé : Personnaliser > Skills > « + » > « + Create skill » > « Upload a skill ». Selon l'aide du 24/11/2026, une page « Plugins » de la barre latérale remplace les onglets Skills, Connectors et Plugins (offres individuelles dès novembre 2026, Team à partir du 30/11/2026) ; le nouveau chemin exact d'import d'un skill n'y est pas décrit : à vérifier dans l'application (https://support.claude.com/en/articles/17740565). Il faut activer « Code execution and file creation » (« Create and edit files » dans la nouvelle présentation), dans Réglages > Capacités pour un compte individuel.
- Selon la page d'aide, l'import est ouvert aux comptes individuels et à chaque membre Team ou Enterprise, sauf si un propriétaire a désactivé la création de skills. En Team, la fonction est active par défaut. En Enterprise, un propriétaire doit activer « Code execution and file creation » et « Skills » (Organization settings > Plugins & skills selon l'aide, > Capabilities selon claude.com/docs). Les propriétaires peuvent aussi mettre un skill à la disposition de tous. Offre Free : incluse selon l'aide, absente de claude.com/docs ; à vérifier.
- Cowork (application de bureau) : il charge les skills et plugins activés sur le compte claude.ai, synchronisés au début de chaque session : après un import, ouvrir une nouvelle session. Pour ces skills et plugins, il ne lit pas le dossier `~/.claude` de la machine. Un projet Cowork regroupe dossiers, instructions, liens et mémoire propre.
- D'après la page mémoire de Claude Code, une session Cowork sur le bureau charge `~/.claude/CLAUDE.md` et `~/.claude/rules/`, sauf les imports qui sortent du dossier de la session et les liens symboliques. Avant de reporter des préférences dans les instructions du projet, vérifier qu'elles n'y sont pas déjà. La lecture d'un CLAUDE.md de projet par Cowork n'est pas documentée : à vérifier dans l'application ; en attendant, mettre les règles dans les instructions du projet Cowork.
- Connecteurs (claude.ai et Cowork) : chaque outil se règle dans Personnaliser > Connecteurs > [connecteur] > Permissions, sur Always allow, Needs approval, Always ask (en déploiement) ou Blocked. Un outil réglé sur Blocked est refusé dans tous les modes de Cowork (Manual, Auto, Skip). En Team ou Enterprise, le propriétaire peut imposer ce réglage (Organization settings > Connectors > [connecteur] > Tools), sans contournement possible ; l'option peut alors manquer côté membre. Hors outils de connecteur, et hors deny d'un outil entier `Bash` ou `WebFetch` (§6, puce Cowork), aucun réglage équivalent n'est documenté : un interdit reste une consigne.
- Projets claude.ai : instructions du projet et fichiers de connaissance. Projets ouverts à toutes les offres (Free : cinq projets au plus ; mode RAG des connaissances réservé aux offres payantes). Instructions de projet sur l'offre Free : l'aide se contredit (sans restriction dans l'article 9517075, « paid plans only » dans l'article 10185728) ; à vérifier, et à défaut coller le texte des instructions en tête de chaque conversation.

## 13. Poser des questions : AskUserQuestion

- Outil de Claude Code qui présente des questions à choix multiples, avec une réponse libre (« Other »). Documenté : une à quatre questions par appel, deux à quatre options chacune, choix multiple possible. Constaté le 07/11/2026 dans l'application de bureau (onglet Code).
- Absent des sous-agents lancés par l'outil Agent : ne jamais déléguer l'entretien à un sous-agent. Absent en `--bare` ; retiré en `-p` avec `--permission-prompts none` ; refusé en mode `dontAsk` ; jamais approuvé automatiquement. Aucune autre restriction n'est documentée.
- Par défaut, une question reste ouverte jusqu'à la réponse. Le réglage `askUserQuestionTimeout` (60s, 5m ou 10m, dans les réglages utilisateur ou `/config`) peut la fermer dans le terminal ; il ne s'applique pas dans l'onglet Code.
- Un skill peut demander à Claude de s'en servir, sans garantie documentée : prévoir la même question en texte numéroté.

## 14. Sessions sans surveillance (tâches programmées, scripts `claude -p`)

- Créer une tâche locale (Claude Desktop 1.1.5368 ou ultérieur) : onglet Code > Scheduled > New task, puis Advanced settings > activer « Only on this computer » et choisir le dossier local. Si cet interrupteur est en haut du dialogue, l'activer avant tout. Si un menu Local/Cloud ou une page pleine s'ouvre (ancien nom : Routines > New routine), choisir Local. Sans cette option, la tâche n'est pas locale (tâche cloud, ou tâche de chat claude.ai) : ni fichiers locaux, ni CLAUDE.md local, ni allow de `~/.claude/settings.json`, et mode auto par défaut pour une tâche cloud. Les points suivants ne s'appliquent alors pas.
- Une tâche locale ne s'exécute que si l'application est ouverte et l'ordinateur éveillé (réglage « garder l'ordinateur éveillé »). Une seule exécution de rattrapage est faite pour le dernier créneau manqué, dans la limite des sept derniers jours.
- Chaque tâche a son propre mode de permission, choisi à la création (sinon, celui des réglages de Claude Code) : le régler sur Accept edits si elle modifie des fichiers. Les règles `allow` de `~/.claude/settings.json` s'appliquent aussi. « Run now » puis « always allow » enregistre des accords propres à la tâche, à relire dans le panneau « Always allowed ».
- Une exécution bloquée sur une demande d'autorisation attend dans sa session, que l'on rouvre depuis l'historique de la tâche pour répondre. Un outil MCP marqué `requiresUserInteraction` bloque chaque exécution. Une exécution peut aussi être sautée (ordinateur en veille, exécution précédente ou autres tâches en cours). L'historique ne prouve donc pas que le travail a été fait : contrôler la présence du résultat attendu.
- Conséquences pour les consignes : préciser dans le maître ce qu'une session programmée doit faire et ne pas faire ; tester une première exécution à la main ; n'autoriser que les commandes nécessaires, nommément.
- Script `claude -p` : il charge CLAUDE.md comme une session normale, sauf avec `--bare`, qui saute CLAUDE.md, skills, hooks et mémoire automatique. `--bare` deviendra le mode par défaut de `-p` : passer alors les consignes explicitement (`--append-system-prompt-file`).

- Version de Claude Code dans le terminal et dans l'onglet Code (§10, `/status`), et pages citées ci-dessus.
- Mode de permission de départ selon l'interface (terminal, VS Code, onglet Code, Cowork), et mods installés face aux deny (§6).
- Dans l'onglet Code : `/context all` (liste « Memory files »), `/status` (ligne « Setting sources »), `/memory`, et réglage « Project instructions ».

- `/context all` après le chargement d'une règle par chemin ; `CLAUDE.md` et `.claude/CLAUDE.md` dans le même dossier (§1, §10).
- Lecture d'un CLAUDE.md de projet par Cowork, et instructions de dossier dans Cowork.
- Deny de `Bash` ou `WebFetch` entier dans Cowork selon le fichier de réglages (§6).
- Motif Read `dossier/*` face aux sous-dossiers ; bloc `env` des réglages et variables `${VAR}` de `.mcp.json` ; accord des serveurs de `.mcp.json` dans une tâche locale programmée (§6).
- Offres et systèmes requis pour l'onglet Code et Cowork, dont le système minimal de Cowork pour un compte claude.ai (§15).
- Import d'un skill sur claude.ai : champs de frontmatter acceptés ; longueur de la description, 1 024 caractères selon claude.com/docs/skills/how-to et la spécification, 200 selon l'article d'aide 12512198 : trancher par un import réel.
- Import de skills selon l'offre (Free, Team, Enterprise), instructions de projet sur l'offre Free, permissions des connecteurs (Always ask en déploiement) (§12).
- AskUserQuestion selon l'interface (terminal, onglet Code, extension VS Code).
- Création d'une tâche locale (« Only on this computer », nom Scheduled ou Routines).
- Après une correction ici : chercher le même fait dans les autres fichiers du kit (dates, numéros de version, mots-clés), puis reconstruire l'archive du skill et le plugin.
